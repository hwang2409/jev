# jm v3 design spec

**Status:** proposal for review
**Date:** 2026-09-23
**Owner:** Henry
**Scope:** design only; this document does not implement jm v3

## 1. decision summary

jm v3 makes the jm library the product. The CLI is a thin shell over the
library. `jgrep`, `jfilter`, and `diff-risk-heat` remain presets over one
judgment engine.

The v3 thesis is the universal Jev adaptor:

- `judge(preset, states)` owns cache lookup, Jev calls, records, and coverage.
- An emitter owns JSONL, pretty output, filtering, and output destinations.
- The CLI parses arguments, forms states, calls the library, and maps the
  result to a process exit code.
- The content-addressed cache remains the dataset flywheel. Every v3 change
  must preserve it.

The ladder is dependency ordered. Each item is one PR-sized change.

| Version | Deliverable |
| --- | --- |
| V1 | reliability and model provenance |
| V2 | `judge()` and emitter refactor |
| V3 | raw-state input and preset parameters |
| V4 | content-addressed cache re-key and deduplication |
| V5 | chunker correctness and state-field validation |
| V6 | gate, score, and calibration semantics |
| V7 | output and composition |
| V8 | preset and CLI polish |

The review window is the place to veto these choices. The ladder does not
re-litigate the v3 thesis.

The following ledger quotes each changed v2 clause and locks its v3
replacement. All other v2 contracts remain in force.

| v2 §4.3: "`gate_values`: the mapped values consumed by gates: Choice `choice`, Score `score`, and Noul `noul`." | V3 Score gates consume the deterministic argmax level. The probability-weighted `score` remains diagnostic only. |

## 3. v3 library contract

### 3.1 state and preset inputs

The public state remains:

```json
{
  "focus": "text to judge",
  "context": {
    "query": "user parameter",
    "heading": "semantic nearby context"
  }
}
```

`state_ref` remains required in the internal `State` object and in output
records. The current `State` shape stores it at `context.state_ref`
(`jm/jm/runner.py:82`). It is not semantic evidence unless a question
explicitly names `context.state_ref`. If a question names that path, the
field appears in both the wire state and the cache key. Otherwise it stays out
of both.

The public `Preset` contains the resolved model, question battery, chunking,
threshold, and output configuration. A preset is still the unit of one Jev
program. The preset name and version remain part of provenance.

### 3.2 `judge()` signature and iterator

The library exposes this sync contract:

```python
def judge(
    preset: Preset | str,
    states: Iterable[State],
    *,
    formation_report: FormationReport,
    cache_store: CacheStore | None = None,
    concurrency: int = 4,
    judge_fn: JudgeFn | None = None,
) -> Iterator[CanonicalRecord]:
    ...
```

The async adapter is named `judge_async` and returns
`AsyncIterator[CanonicalRecord]` with the same arguments and contracts. Neither
adapter exposes HTTP details.

Formation stays outside the library core. The CLI or another caller chunks
input and passes the resulting typed report to `judge()`:

```python
@dataclass(frozen=True, slots=True)
class FormationEvent:
    kind: Literal["skip", "input_error"]
    reason: Literal["scan_cap", "context_limit", "prefiltered", "input_error"]
    message: str
    state_ref: str | None
    source_ref: str | None
    boundary: str | None


@dataclass(frozen=True, slots=True)
class FormationReport:
    events: tuple[FormationEvent, ...]
    diagnostics: tuple[Diagnostic, ...]
```

`skip` events require `state_ref` and have a reason of `scan_cap`,
`context_limit`, or `prefiltered`. `input_error` events require `source_ref`
and have no `state_ref`. `FormationReport` contains one event per rejected
input or formed-state skip. The judge merges these events with formed states
when it builds coverage and emits their canonical error records. It does not
re-run chunking.

The iterator has these rules:

- It is lazy. Calling `judge()` does not make a network request or write output.
- It eagerly consumes and validates the complete finite `states` iterable and
  the complete `formation_report` before the first judgment call. This includes
  duplicate `state_ref` detection across the complete input.
- It yields judgment records as calls complete. It does not promise input order.
  Output-side iteration remains streaming; input-side streaming is not a v3
  feature.
- It yields one `result`, `partial_result`, or `error` record per judged state.
- It yields typed `diagnostic` records in the same stream for validator warnings,
  concurrency backoff and restore events, and other runtime diagnostics.
- It yields the typed formation events as canonical error records.
- It yields exactly one terminal `coverage` record after the state iterable ends.
- The terminal record is the only source of complete or partial coverage truth.

Invalid preset data, invalid options, and invalid policy syntax raise
`ConfigurationError` before the iterator yields records. Duplicate state
references are input data errors: the library raises typed `InputError` before
any judge or cache call. The CLI catches that error, emits the coverage/skip
summary, and exits 2. Configuration errors are for invalid options or presets
and map to exit 64, never for input data. An API failure, malformed answer, or
exception from an injected judge becomes a per-state `error` record with a safe
message. Independent states continue. A caller never receives a raw gateway
exception or credential.

The coverage counts keep the v2 equation:

```text
discovered = judged + skipped
```

`judged` includes cache hits and states that produce an operational error.
`emitted` counts per-state records before output filtering. `failed` counts
judged states with an operational error or partial answer. Input errors before
state formation are not discovered states. A gate still exits 2 for any
coverage reason, input error, or fewer than `require_states` judged states.

### 3.3 emitter contract

The public configuration exception is `ConfigurationError`. The public input
exception is typed `InputError`; it represents malformed or duplicate input
data and is distinct from configuration failure.

```python
@dataclass(frozen=True, slots=True)
class Diagnostic:
    severity: Literal["info", "warning", "error"]
    code: str
    message: str
    path: str | None
    source_ref: str | None


@dataclass(frozen=True, slots=True)
class DiagnosticRecord:
    record_type: Literal["diagnostic"]
    diagnostic: Diagnostic


@dataclass(frozen=True, slots=True)
class InputSidecar:
    values: Mapping[str, Mapping[str, JSONValue] | Path]
```

Validators return `tuple[Diagnostic, ...]`. `path` identifies a preset or
question field. `source_ref` identifies an input line. The library never
writes diagnostics to stderr.

```python
@dataclass(frozen=True, slots=True)
class ResultFilter:
    kind: Literal["keep", "policy"]
    question_id: str | None
    operator: Literal["<", "<=", ">", ">=", "==", "!="] | None
    threshold: float | int | None
    expression: str | None


@dataclass(frozen=True, slots=True)
class EmitResult:
    records_written: int
    records_suppressed: int
    diagnostics_written: int
    coverage: CoverageRecord
    passthrough: bool
    broken_pipe: bool
```

`ResultFilter(kind="keep")` requires `question_id`, `operator`, and
`threshold`, with `operator=">="`, and has no `expression`.
`ResultFilter(kind="policy")` requires `expression` and has no threshold
fields. `records_written` counts canonical records written to a sink;
`records_suppressed` counts successful result records hidden by the filter.
`diagnostics_written` counts typed diagnostic records routed to stderr.
`EmitResult.coverage` is the one terminal coverage record consumed by the
emitter. `broken_pipe` is true only when the emitter stopped after
`BrokenPipeError`; it does not change coverage.

The emitter consumes records and does not call Jev:

```python
def emit(
    records: Iterable[CanonicalRecord],
    *,
    format: Literal["jsonl", "pretty"] = "jsonl",
    emit_mode: Literal["judgment", "input"] = "judgment",
    jsonl_stream: TextIO,
    pretty_stream: TextIO,
    output_path: Path | None = None,
    result_filter: ResultFilter | None = None,
    input_sidecar: InputSidecar | None = None,
) -> EmitResult:
    ...
```

The emitter contract is:

- JSONL serializes each non-diagnostic canonical record once, in iterator
  order. Diagnostic records are never JSONL in either output mode.
- Diagnostic records are typed variants in the single `judge()` iterator
  stream. They include validator warnings, concurrency backoff and restore
  events, and other runtime diagnostics. The emitter routes them to stderr in
  both `jsonl` and `pretty` modes. Library callers see the records directly.
- A result filter can suppress only successful result records. Error,
  partial-result, skip-summary, and coverage records remain visible.
- `pretty` writes selected human rows to `pretty_stream`. Canonical JSONL still
  goes to the JSONL sink.
- `output_path` redirects canonical JSONL to that file. The file is opened only
  by the emitter and is closed by it. Pretty output remains on stderr.
- `input_sidecar` maps each `state_ref` to its original JSON record or its
  normalized file `Path`. It is required for `emit_mode="input"` and is never
  sent to Jev or added to the cache key.
- The emitter does not change coverage counts or record contents.
- `FormationReport.diagnostics` stays input-side. `EmitResult` retains only
  counts and outcome fields, not diagnostic objects.
- The emitter catches `BrokenPipeError`, closes the broken stream, and returns
  `EmitResult(broken_pipe=True)`. It never raises the exception. The CLI exits
  0 without a traceback, as locked by the V1 SIGPIPE quiet-exit task.

The gate evaluator consumes result records separately. It never evaluates
pretty text or filtered output.

### 3.4 thin CLI boundary

The CLI does only five jobs: parse options, resolve a preset, form states,
call `judge()`, and call the emitter. It may evaluate a gate after the record
iterator is consumed. It must not contain a second Jev client, cache lookup,
answer parser, retry loop, or record serializer.

## 4. locked design decisions

### 4.1 retry set and concurrency

The retryable HTTP status set is `{429, 503, 504, 529}`. Timeouts remain
retryable. A 503 or 504 has no required `Retry-After` header, so the client uses
bounded exponential backoff with jitter. If a finite header exists, the client
honors it up to the configured maximum. It never retries auth, validation, or
other 4xx responses.

The observed 503 body is a normal Gateway error object:

```json
{
  "error": {
    "type": "service_unavailable_error",
    "message": "Service temporarily unavailable. Please try again shortly."
  }
}
```

The client treats the HTTP status as the retry signal. It does not require a
new error-body type or a `Retry-After` header for 503 or 504.

The default attempt budget stays three. Concurrency uses one mechanism:
capped static concurrency. The default is four in-flight calls and the hard
cap is eight. A requested value above eight is accepted, capped to eight, and
returns a structured warning diagnostic:

```text
code=concurrency_capped severity=warning requested=12 effective=8 cap=8
```

Two consecutive 503 responses halve the current in-flight limit, down to one.
After one clean minute with no 503 response, the limit restores one step at a
time toward the configured effective value. Each change returns a structured
diagnostic:

```text
code=concurrency_backoff severity=warning status=503 consecutive=2 effective=4
code=concurrency_restored severity=info clean_seconds=60 effective=8
```

The library returns these diagnostics. The CLI emitter renders them to stderr.
No library-core path writes stderr. The default never exceeds four.

This preserves the observed zero-error operating point at concurrency four and
limits the 30-second stalls seen at higher concurrency.

### 4.2 model provenance

`model` in a preset is any non-empty model ID accepted by the selected Gateway
transport. Preset validation no longer hard-codes one string. The request uses
the resolved model ID in the gateway model header.

Every result, partial result, error, skip-summary, and coverage record has
`meta.served_model`. It is the observed provider model or the string
`"unknown"`. Every cache entry stores the same value when known and stores
`"unknown"` when the call returned no provenance. `meta.model` remains the
configured model ID.

Served-model extraction uses this exact order: first
`providerMetadata.gateway.routing.canonicalSlug`; otherwise the
`canonicalSlug` from the final successful entry in
`providerMetadata.gateway.modelAttempts`; otherwise `"unknown"`. A routing
slug wins even when model attempts also exist. An unsuccessful or missing
attempt does not provide provenance.

Calibration compares observed model values. A mixed baseline or candidate set
is operationally indeterminate and exits 2. A single model change is reported
as drift and uses the normal tolerance decision.

### 4.3 Score gate semantics

For a Score answer, a threshold such as `fail_at_least: 2` gates on the
argmax level, not on the probability-weighted expected `score` field. The
argmax is the level key with the largest probability. Ties choose the highest
level so a risk gate fails conservatively. The output still exposes the
probability-weighted `score` as a diagnostic value.

This makes an ordinal threshold mean what its name says. A distribution with
`P(level 2) = 0.75` trips `>= 2` even when its expected score is 1.72. A
distribution with `P(level 2) = 0.99` and `P(level 1) = 0.01` also trips it.
Calibration records both the expected-score delta and the argmax level crossing,
but pass/fail uses the argmax crossing.

### 4.4 boundary noise

Calibration noise far from every configured gate threshold is diagnostic only.
It sets `far_side_noise: true` and does not void the verdict. Noise within the
configured threshold margin, or noise that straddles a threshold, sets
`boundary_noise: true` and makes `within_tolerance: null` with exit 2.

The same rule applies to Score argmax levels and numeric Noul thresholds. A
candidate that changes an argmax far from a configured threshold is still
reported as drift, but it sets `far_side_noise` rather than
`boundary_noise` solely for changing.

### 4.5 schema loosening boundary

Jm validates its known question fields. The top-level question object is open:
unknown top-level keys pass through unchanged with a warning. Criterion objects
are also open: unknown criterion fields pass through unchanged with a warning.
The following jm-interpreted blocks remain closed and fail closed:

- chunking and effective defaults;
- state and context limits;
- thresholds and gate operators;
- cache key-envelope fields;
- coverage counts and reason enums;
- emitter configuration.

The validator returns one structured warning diagnostic per unknown path. The
CLI emitter renders those diagnostics to stderr. It still validates the
question type, required instructions, state fields, and criteria required to
form the wire request. V3 locks the proven boundary: Noul criteria remain the
two `true` and `false` criteria required by the boolean wire conversion. Score
criteria accept exactly three or exactly four ordered levels. The exact
pass-through paths are `questions.<id>.<unknown-top-level-key>` and unknown
fields in each `questions.<id>.criteria[0..2]` or `[0..3]` criterion object,
after validation. The client sends the accepted question body unchanged,
except for Noul's `type: boolean` wire conversion. Arbitrary score level
counts are a v3 non-goal until each count has a passing wire and parser
fixture. The wire uses only the three- and four-level shapes, and answer
normalization maps those levels to `0..n-1`. The implementation must not invent
API capabilities.

### 4.6 cache invariant

The cache remains content addressed and complete-answer only. The key is the
equality relation: two requests are equivalent if and only if their one
canonical key envelopes hash equal. The envelope is defined once in section
6.1. It contains request identity, not provenance. Configured model, preset
display name, preset version, and served model are stored-entry provenance and
do not appear in the key envelope.

The bytes hashed are the bytes sent. The client builds one canonical wire
payload, with sorted object keys and UTF-8 JSON without insignificant spaces.
The `state` member sent in that payload is exactly the `wire_state` member in
the stored entry and in the key envelope's request. A cache hit reuses the
complete response for that exact payload; jm never hashes a broader state and
sends a narrower one. Failed and partial calls never publish a complete
answer. Coverage still reports cache hits as judged states.

Distillation remains a non-goal pending Henry's TypeSafe Terms of Service check.
The cache-as-dataset flywheel remains in scope.

## 5. v3 input and preset semantics

### 5.1 raw states

V3 adds `--by state`. It reads one JSON object per JSONL line with this exact
shape:

```json
{
  "state_ref": "case-17",
  "focus": "text to judge",
  "context": {
    "heading": "release",
    "query": "contains the launch decision"
  }
}
```

`state_ref` and `focus` are required. `context` is required and must be an
object. Unknown context keys are allowed because raw states are the universal
adaptor input, but jm still applies byte limits. Duplicate or empty state refs
are input errors with a source locator. A raw-state input error is not a formed
state, so it does not increase `discovered` and makes coverage partial.

The `state_ref` is preserved in result and error records. The formed
`State` stores it at `context.state_ref`. It is excluded from the wire and
cache projection unless a question names `context.state_ref`, as defined in
section 6.1. V3 presets opt into raw-state input by listing `state` in their
`compatible_chunkers` list. V1 and v2 presets remain excluded because their
existing lists are closed contracts. The migration adds `state` only when a
preset is rewritten as `jm.preset/v3`; it does not silently change an existing
v1 or v2 preset.

### 5.2 preset parameters

Every `jm.preset/v3` preset has this explicit declaration block:

```yaml
parameters:
  declared: [query, predicate]
```

`declared` is a duplicate-free list of parameter names. A missing declaration
block is a usage error with exit 64. A supplied `--param` not in the declared
list is also a usage error. A declared parameter referenced by a question but
not supplied by the invocation is a usage error with exit 64. A question that
references a context field that is neither in the effective chunker's built-in
inventory nor in `parameters.declared` returns a warning diagnostic naming the
question and field; jm does not synthesize the field.

V3 adds repeatable `--param key=value`. Each parameter is a string mapped to
`context.key` before validation and cache lookup. A key must match
`[a-z][a-z0-9_]*`. The final parameter set must satisfy every parameter field
named by `state_fields`.

An unknown parameter is a usage error with exit 64. A missing required
parameter is a usage error with exit 64. Duplicate keys are a usage error.
The existing `--query` and `--predicate` short forms remain aliases that map to
the same parameter path. They cannot conflict with `--param`.

Parameters are invocation data, not preset text. They appear in formed state
context and in the semantic cache projection when a question names them.

### 5.3 state-field validation

The effective chunker declares its context keys. V3 uses this inventory:

| Chunker | Context keys |
| --- | --- |
| `state` | keys supplied by the raw state, plus `parameters.declared` |
| `file` | `language`, `metadata`, `path`, plus `parameters.declared` |
| `line` | `line`, `source`, `surrounding`, `unit`, plus `parameters.declared` |
| `para` | `heading`, `paragraph`, `source`, `surrounding`, `unit`, plus `parameters.declared` |
| `record` | `metadata`, `unit`, plus `parameters.declared` |
| `hunk` | `changed_tests`, `file`, `hunk_header`, `surrounding`, `unit`, plus `parameters.declared` |

`state_fields` may name `focus`, `context.state_ref`, or `context.<key>`. If a
question names a context key that the effective chunker cannot provide,
jm returns a warning diagnostic naming the question, field, and chunker. The
CLI emitter renders it to stderr. The run continues. The absent field is not
synthesized. This warning does not change exit code or coverage counts.

## 6. cache v3

### 6.1 re-key rule

The v3 key envelope is defined once. The cache hashes this exact object:

```json
{
  "cache_schema": "jm-answer/v3",
  "wire_request": {
    "providerOptions": {"gateway": {"zeroDataRetention": true}},
    "state": {
      "focus": "...",
      "context": {"query": "...", "heading": "..."}
    },
    "questions": {"...": "..."}
  }
}
```

The `wire_request` object is the exact request object sent to the transport.
The cache hashes the canonical UTF-8 JSON bytes of the envelope, with sorted
object keys and no insignificant spaces. Two requests are equivalent if and
only if these envelope hashes equal. The envelope has no configured-model,
preset-name, preset-version, served-model, or other provenance field.

Before lookup, the client derives `wire_state` and inserts it as the request's
`state` member. The projection is an allowlist algorithm:

1. Include the complete `focus` value.
2. For every `state_fields` path named by any question in the battery, include
   that path's value. A `context.<key>` path reads from `context.<key>`;
   `context.state_ref` is the single state-reference path.
3. If consistency sampling is active, include `context.uid` in the wire
   context, even when no question names it. A question may not name
   `context.uid`.
4. Include nothing else from `context`.

Missing named fields follow the state-field validation contract and are never
synthesized. Every context
field not positively named by the battery is excluded by construction. This
includes the chunker-generated `context.subunit` (`jm/jm/chunkers.py:92`) and
all other chunker, raw-state, and future fields. A context field influences
judgment only when the battery names it. This makes the bytes hashed equal to
the bytes sent by definition. Position text inside `focus` remains part of
`focus`.

### 6.2 battery deduplication

The resolved question battery is stored once under a content hash scoped to
`(preset, preset_version, question_battery_hash)`. A cache entry stores the
reference and the battery hash, not a repeated copy of the full battery. An
export resolves the reference and emits the same v2 training-shaped fields.

The battery hash changes when any interpreted question text, criteria, type,
state field, or pass-through wire field changes.

Calibration uses
`calibration_case_id = sha256(canonical_json({"cache_key": cache_key,
"wire_state": wire_state, "question_battery_ref": ref}))`. A v3 cache entry
has this complete persisted shape:

```json
{
  "cache_schema": "jm-answer/v3",
  "cache_key": "sha256:...",
  "key_envelope": {
    "cache_schema": "jm-answer/v3",
    "wire_request": {"providerOptions": {}, "state": {}, "questions": {}}
  },
  "wire_state": {"focus": "...", "context": {"query": "..."}},
  "question_battery_ref": {
    "preset": "jgrep",
    "preset_version": "1",
    "battery_hash": "sha256:..."
  },
  "configured_model": "typesafe-ai/jev",
  "served_model": "jev-1.13.0",
  "usage": {"input_tokens": 120, "output_tokens": 20},
  "created_at": "2026-09-23T12:34:56+00:00",
  "state_refs": ["case-17", "case-22"],
  "response": {"answers": {}}
}
```

`key_envelope` is the section 6.1 envelope copied into the stored entry.
`question_battery_ref` includes the preset name, preset version, and battery
hash. `usage` is normalized numeric usage. `created_at` is the publication
time. `state_refs` is sorted and may contain several merged input references.
The response is complete and carries the normalized answers. The entry stores
both configured and served model values, using `unknown` when served
provenance is absent.

V4 reads `cache_key` and `key_envelope` for equality and deduplication. V6
reads `cache_key`, `wire_state`, `question_battery_ref`, `state_refs`, the
response, both model fields, and normalized usage for calibration. V7 reads
`usage` and `created_at` for cached metrics. No consumer reads a field outside
this schema. The candidate calibration call reuses `wire_state`; it does not
reconstruct a state reference from a top-level wire field or from the key.
Calibration emits all `state_refs` in its comparison record. If
`context.state_ref` is named by the battery, entries cannot merge different
references because that path is part of `wire_state` and the key.

Presets that use v3-only features declare `jm.preset/v3`. V1 and v2 preset
files remain readable for migration and inspection, but they cannot request
v3-only chunkers, parameters, or output modes without an explicit schema update.

### 6.3 invalidation and counts

The cache schema changes to `jm-answer/v3`. V3 performs one full cache
invalidation at rollout. This is an accepted migration cost because old keys
contain the fields that v3 must remove. Later key changes are content based.

Cache hits remain judged states. They contribute one to `judged`, one to
`emitted` before filtering, and zero to `failed`. A cache hit does not make a
network call.

## 7. chunkers and state formation

### 7.1 bounded surrounding context

When surrounding material exceeds `context_field_bytes`, the chunker truncates
it to a deterministic UTF-8 boundary and adds the ASCII marker
`[... surrounding truncated ...]`. The final field stays within the limit.
The chunk is judged, not rejected, and coverage does not gain a
`context_limit` skip for this case. Required identity, parameter, and complete
state limits still fail closed.

### 7.2 library defaults

Calling a library chunker without a rejection collector must not crash on an
ordinary markdown document only because a neighbour is large. The safe default
is the same bounded behavior as the CLI. A caller may still choose a strict
mode for tests, but the public default forms a state with bounded context.

### 7.3 hunk parser

The hunk parser validates body lines against unified diff syntax. A body line
must begin with a space, `+`, `-`, or the exact no-newline marker. A line with
any other prefix ends the current hunk parse and produces an `input_error`
with a source locator. It must not swallow later file headers or hunks.

Valid zero-count hunks, quoted paths, renames, deletes, binaries, CRLF, and
the no-newline marker keep their existing parse behavior.

### 7.4 paragraph and file behavior

The paragraph chunker skips units that contain only a Markdown heading. The
heading remains available as `context.heading` on the next meaningful unit.

`--by file` remains a whole-file mode. If the focus exceeds `focus_bytes`, jm
rejects it with a `context_limit` skip and documents this behavior in help.
V3 does not silently split a file into arbitrary byte fragments. Callers that
need splitting use `--by para`, `--by line`, or `--by state`.

The `context_lines` key is removed from the hunk preset because the hunk
chunker does not consume it. Hunk context comes from the supplied unified diff.

### 7.5 metadata and fields

V5 exposes `--metadata-fields key[,key...]` for record input. The selected
fields populate `context.metadata` and are included in the semantic cache
projection only when questions name them.

The chunker and state-field rules are validated before Jev calls. The returned
warning diagnostic for an unavailable context field does not create a fake
value, a partial answer, or an extra coverage count.

## 8. gate and calibration semantics

### 8.1 empty input

An empty finite input produces no input-error record. The CLI emitter renders
`jm: no hunks found` for empty hunk input, or `jm: no states found` for other
empty input. Its coverage record is complete with all five counts equal to
zero. It has no coverage reason.

For a gate with `--require-states 1`, the gate exits 2 for too few states. With
`--require-states 0`, ordinary vacuous truth applies: `any(...)` is false and
`all(...)` is true. Because a policy is a failure condition, the former exits
0 and the latter exits 1. The output still has one terminal coverage record.

Binary-only or header-only diffs use the same no-hunks message. They do not
become an API failure.

### 8.2 policy filter

`run` and `jfilter` add a policy filter that reuses the gate grammar:

```text
jm jfilter 'describes a failed payment' --filter policy \
  --filter-policy 'any(satisfies_predicate.noul >= 0.75)'
```

The policy is evaluated per result record. A matching record is emitted. A
non-matching successful result is suppressed. Errors, partial results, skip
summaries, and coverage remain visible. The filter does not change coverage
counts. A selection filter is not a gate: no matching result still exits 0
when coverage is complete. Incomplete coverage or an operational error exits 2.
The filter never produces exit 1. Invalid filter syntax or an invalid option
combination exits 64.

`--filter=keep` remains as the short form for one preset-owned keep threshold.

### 8.3 calibration

Calibration uses the same effective gate value as the gate evaluator. For
Score thresholds, it records `baseline_argmax`, `candidate_argmax`, and
`argmax_crossing`; it does not use the expected score to decide a threshold
crossing.

Calibration submits candidate cases through the shared runner pool. The
default concurrency is four, and the same retry and capped-concurrency policy
applies. Candidate calls never read or overwrite the baseline cache entry.

Each calibration case has this contract:

```json
{
  "record_type": "calibration_comparison",
  "calibration_version": "jm.calibration/v3",
  "calibration_case_id": "sha256:...",
  "cache_entry": {
    "cache_key": "sha256:...",
    "state_refs": ["case-17", "case-22"],
    "question_battery_ref": {
      "preset": "jgrep",
      "preset_version": "1",
      "battery_hash": "sha256:..."
    }
  },
  "comparisons": [
    {
      "question_id": "risk",
      "primitive": "score",
      "baseline_answer": {},
      "baseline_usage": {"input_tokens": 120, "output_tokens": 20},
      "candidate_repeats": [
        {"answer": {}, "usage": {"input_tokens": 121, "output_tokens": 20}, "served_model": "jev-1.14.0"}
      ],
      "gate_values": {"baseline": 1, "candidate": 2},
      "choice_flip": false,
      "probability_delta": 0.0,
      "baseline_argmax": 1,
      "candidate_argmax": 2,
      "argmax_crossing": true,
      "score_delta": 0.2,
      "noul_delta": 0.0,
      "derived_confidence": {"baseline": 0.8, "candidate": 0.8},
      "thresholds": []
    }
  ],
  "provenance": {
    "baseline_model": "jev-1.13.0",
    "candidate_models": ["jev-1.14.0"]
  },
  "boundary_noise": false,
  "far_side_noise": true,
  "within_tolerance": true
}
```

There is one comparison record per complete cache entry, not one record per
question. `comparisons` contains every question in the battery. Each question
comparison includes the baseline answer and usage, every ordered candidate
repeat with usage and served model, the gate value fields, threshold details,
and the primitive-specific deltas. `state_refs` is the full plural reference
set from the entry. The record preserves mixed-model evidence rather than
discarding a repeat.

`boundary_noise` is verdict-affecting. It is true only when a changed value is
near a configured threshold or straddles it. `far_side_noise` is diagnostic.
It is true when repeats disagree far from every configured threshold. Far-side
noise does not set `within_tolerance` to null and does not force exit 2.
The final summary is one record with this shape:

```json
{
  "record_type": "calibration_summary",
  "calibration_version": "jm.calibration/v3",
  "preset": "jgrep",
  "preset_version": "1",
  "repeats": 1,
  "comparison_count": 30,
  "qualified_cases": 30,
  "baseline_model_counts": {"jev-1.13.0": 30},
  "candidate_model_counts": {"jev-1.14.0": 30},
  "boundary_noise_cases": 0,
  "far_side_noise_cases": 2,
  "choice_flips": 0,
  "max_probability_delta_observed": 0.02,
  "max_score_delta_observed": 0.2,
  "max_noul_delta_observed": 0.02,
  "threshold_crossings": 0,
  "stable_drift_cases": 0,
  "tolerances": {},
  "within_tolerance": true
}
```

The summary uses `boundary_noise_cases` and `far_side_noise_cases`, never the
ambiguous single v2 noise count. It includes model counts, observed maxima,
tolerances, the calibration version, and `within_tolerance`. The summary and
comparison records are the complete v3 replacement for the v2 per-question
case record and summary.

The calibration exit codes remain:

| Code | Meaning |
| --- | --- |
| `0` | qualifying cases completed and all tolerances passed |
| `1` | observed drift exceeded a configured tolerance |
| `2` | operational error, mixed model provenance, boundary noise, or no qualifying cases |
| `64` | invalid command, preset, or tolerance |

`no qualifying cases` is not a passing zero delta. It produces a summary with
`within_tolerance: null` and exit 2.

## 9. output and composition

### 9.1 metrics

The default result record remains compact. `--metrics` opts into:

```json
{
  "meta": {
    "usage": {"input_tokens": 120, "output_tokens": 20},
    "latency_ms": 312
  }
}
```

The terminal coverage record then adds `usage_totals` and `latency_ms_total`.
Usage sums only numeric fields from each result or the persisted entry's
normalized `usage`. Cache hits contribute stored usage and zero new latency.
Without `--metrics`, these fields are absent from per-state and coverage
output. This keeps the default record contract stable.

### 9.2 jfilter passthrough

`jm jfilter --emit=input` re-emits the original JSON object for every matching
record. It is supported for exactly `--by record` and `--by file`. Record mode
emits the original JSON object. File mode emits the normalized input path.
Both values are held in the `input_sidecar` emitter argument. They are never
sent to Jev as an extra state field or added to the cache key envelope.

The canonical judgment JSONL remains available with the default emitter mode.
In passthrough mode, stdout contains only matching input objects or paths. The
emitter writes non-result records and the terminal coverage record as JSONL to
stderr, including every diagnostic record, and keeps the selection-filter exit
rules. This is the one intentional stdout exception to the canonical judgment
stream, because passthrough must compose as a grep-like input stream.

### 9.3 input and streaming

`--input -` means stdin. It is equivalent to omitting `--input`. A literal
filesystem path named `-` requires an explicit path form that resolves to a
file.

The runner validates the complete finite input before its first judgment call.
It yields result records as judgments complete. It does not wait for every
judgment to complete before yielding the first result. A downstream `head` may
close the pipe; jm exits quietly after closing the broken stream. States that
already completed may remain cached, which is allowed and documented.

## 11. compatibility and exit contract

The v3 judgment exit codes remain:

| Code | Meaning |
| --- | --- |
| `0` | complete coverage and no active failure condition |
| `1` | a complete gate or policy filter found the requested failure condition |
| `2` | operational error, incomplete coverage, too few required states, or an indeterminate gate |
| `64` | invalid command, preset, parameter, policy, or option combination |

Selection commands use this separate exit table:

| Code | Selection meaning |
| --- | --- |
| `0` | complete coverage, whether or not any result matched |
| `2` | incomplete coverage or operational error |
| `64` | invalid filter, preset, parameter, or option combination |

Only a gate or an explicit failure-condition policy may return exit `1`.

`judge()` does not return an exit code. The CLI derives it from terminal
coverage and gate results. A library caller can inspect the same `CoverageRecord`
and `GateResult` data without parsing text.

The terminal coverage record always has exactly these five count fields:
`discovered`, `judged`, `emitted`, `skipped`, and `failed`. V3 adds optional
metric totals, not a second count system. The invariant remains:

```text
discovered = judged + skipped
failed <= judged
```

Output filtering does not reduce `emitted`. It only suppresses visible result
records. This prevents a filtered empty output from claiming that no states
were judged.

## 12. non-goals

V3 carries forward these v2 non-goals:

- watch mode, unbounded input streaming, streaming windowing, and incremental
  windowing;
- a `--hint` option or query expansion;
- injection hardening for hostile or multi-tenant state;
- a native TypeSafe API fallback or a second transport;
- embeddings, a vector database, a hosted search service, or a heavy prefilter;
- automatic threshold updates;
- a remote or shared cache;
- generated explanations, model prose, broad policy language, and arithmetic
  inside Jev questions;
- local model training or distillation before Henry's TypeSafe Terms of Service
  check.

V3 streaming means lazy finite output iteration. It does not reopen watch mode,
unbounded input, streaming windowing, or incremental windowing. Interpreting a
future question key such as `hint` is also a non-goal; an unknown key may pass
through, but jm does not assign it semantics. V3 model provenance does not
reopen distillation or a second backend. V3 raw-state input does not make
arbitrary hostile state safe for CI.
