# jm v3 design spec

**Status:** proposal for review
**Date:** 2026-09-23
**Owner:** Henry
**Scope:** design only; this document does not implement jm v3

## 1. decision summary

jm v3 makes the jm library the product. The CLI is a thin shell over the
library. `jgrep`, `jfilter`, and `diff-risk-heat` remain presets over one
judgment engine.

The v3 thesis is the universal Jev adaptor:

- `judge(preset, states)` owns cache lookup, Jev calls, records, and coverage.
- An emitter owns JSONL, pretty output, filtering, and output destinations.
- The CLI parses arguments, forms states, calls the library, and maps the
  result to a process exit code.
- The content-addressed cache remains the dataset flywheel. Every v3 change
  must preserve it.

The ladder is dependency ordered. Each item is one PR-sized change.

| Version | Deliverable |
| --- | --- |
| V1 | reliability and model provenance |
| V2 | `judge()` and emitter refactor |
| V3 | raw-state input and preset parameters |
| V4 | content-addressed cache re-key and deduplication |
| V5 | chunker correctness and state-field validation |
| V6 | gate, score, and calibration semantics |
| V7 | output and composition |
| V8 | preset and CLI polish |

The review window is the place to veto these choices. The ladder does not
re-litigate the v3 thesis.

### 2.2 v2 amendments

jm v3 amends the locked v2 contract in these places:

1. v2 says the client retries HTTP 429 and 529 only. V3 adds HTTP 503 and 504
   with bounded backoff. The v1 and v2 attempt budget remains three by default.
2. v2 keys the cache on the resolved state. V3 removes identity and position
   fields from the cache preimage and accepts one full cache invalidation.
3. v2 compares Score thresholds against the probability-weighted `score`.
   V3 gates Score thresholds on the argmax level. Calibration uses the same
   gated level.
4. v2 treats empty input as an input error. V3 treats an empty finite input as
   zero states. `--require-states 0` then enables the normal vacuous gate rules.
5. v2 makes `Runner.run` a stream-writing API. V3 makes `judge()` the library
   API and moves rendering to an emitter.
6. v2 rejects every model except `typesafe-ai/jev`. V3 accepts a non-empty
   model ID, records the served model, and lets calibration detect drift.
7. v2 closes every preset block. V3 keeps jm-interpreted blocks closed, but
   passes unknown fields in question bodies to the Jev wire with a warning.

All other v2 contracts remain in force unless this document states a change.

## 3. v3 library contract

### 3.1 state and preset inputs

The public state remains:

```json
{
  "focus": "text to judge",
  "context": {
    "query": "user parameter",
    "heading": "semantic nearby context"
  }
}
```

`state_ref` remains required in the internal `State` object and in output
records. It is not semantic evidence unless a question explicitly names it.
The cache never uses it.

The public `Preset` contains the resolved model, question battery, chunking,
threshold, and output configuration. A preset is still the unit of one Jev
program. The preset name and version remain part of provenance.

### 3.2 `judge()` signature and iterator

The library exposes this sync contract:

```python
def judge(
    preset: Preset | str,
    states: Iterable[State],
    *,
    cache_store: CacheStore | None = None,
    concurrency: int = 4,
    judge_fn: JudgeFn | None = None,
) -> Iterator[CanonicalRecord]:
    ...
```

The async API has the same data contract and returns an async iterator. The
exact adapter name may differ, but it must not expose HTTP details.

The iterator has these rules:

- It is lazy. Calling `judge()` does not make a network request or write output.
- It consumes finite states and yields per-state records in input order.
- It may keep only a bounded in-flight window. It must not build a list of all
  responses before yielding the first record.
- It yields one `result`, `partial_result`, or `error` record per judged state.
- It yields skip-summary errors for formed states that are not judged.
- It yields exactly one terminal `coverage` record after the state iterable ends.
- The terminal record is the only source of complete or partial coverage truth.

Invalid preset data, invalid options, duplicate state references, and invalid
policy syntax raise a typed configuration exception before the iterator yields
records. An API failure, malformed answer, or exception from an injected judge
becomes a per-state `error` record with a safe message. Independent states
continue. A caller never receives a raw gateway exception or credential.

The coverage counts keep the v2 equation:

```text
discovered = judged + skipped
```

`judged` includes cache hits and states that produce an operational error.
`emitted` counts per-state records before output filtering. `failed` counts
judged states with an operational error or partial answer. Input errors before
state formation are not discovered states. A gate still exits 2 for any
coverage reason or for fewer than `require_states` judged states.

### 3.3 emitter contract

The emitter consumes records and does not call Jev:

```python
def emit(
    records: Iterable[CanonicalRecord],
    *,
    format: Literal["jsonl", "pretty"] = "jsonl",
    emit_mode: Literal["judgment", "input"] = "judgment",
    jsonl_stream: TextIO,
    pretty_stream: TextIO,
    output_path: Path | None = None,
    result_filter: ResultFilter | None = None,
) -> EmitResult:
    ...
```

The emitter contract is:

- JSONL serializes each canonical record once, in iterator order.
- A result filter can suppress only successful result records. Error,
  partial-result, skip-summary, and coverage records remain visible.
- `pretty` writes selected human rows to `pretty_stream`. Canonical JSONL still
  goes to the JSONL sink.
- `output_path` redirects canonical JSONL to that file. The file is opened only
  by the emitter and is closed by it. Pretty output remains on stderr.
- The emitter does not change coverage counts or record contents.
- A broken JSONL sink raises `BrokenPipeError` to the CLI boundary. The CLI
  closes the stream and exits 0 without a traceback.

The gate evaluator consumes result records separately. It never evaluates
pretty text or filtered output.

### 3.4 thin CLI boundary

The CLI does only five jobs: parse options, resolve a preset, form states,
call `judge()`, and call the emitter. It may evaluate a gate after the record
iterator is consumed. It must not contain a second Jev client, cache lookup,
answer parser, retry loop, or record serializer.

## 4. locked design decisions

### 4.1 retry set and concurrency

The retryable HTTP status set is `{429, 503, 504, 529}`. Timeouts remain
retryable. A 503 or 504 has no required `Retry-After` header, so the client uses
bounded exponential backoff with jitter. If a finite header exists, the client
honors it up to the configured maximum. It never retries auth, validation, or
other 4xx responses.

The observed 503 body is a normal Gateway error object:

```json
{
  "error": {
    "type": "service_unavailable_error",
    "message": "Service temporarily unavailable. Please try again shortly."
  }
}
```

The client treats the HTTP status as the retry signal. It does not require a
new error-body type or a `Retry-After` header for 503 or 504.

The default attempt budget stays three. The default in-flight request count
stays four. `--concurrency` may accept a higher value for explicit experiments,
but the runner caps active work at a configured safety ceiling or reduces the
window after a 503/504 burst. The chosen mechanism must make the effective
window visible in stderr and must never raise the default above four.

This preserves the observed zero-error operating point at concurrency four and
limits the 30-second stalls seen at higher concurrency.

### 4.2 model provenance

`model` in a preset is any non-empty model ID accepted by the selected Gateway
transport. Preset validation no longer hard-codes one string. The request uses
the resolved model ID in the gateway model header.

Every result, partial result, error, skip-summary, and coverage record has
`meta.served_model`. It is the observed provider model or the string
`"unknown"`. Every cache entry stores the same value when known and stores
`"unknown"` when the call returned no provenance. `meta.model` remains the
configured model ID.

Calibration compares observed model values. A mixed baseline or candidate set
is operationally indeterminate and exits 2. A single model change is reported
as drift and uses the normal tolerance decision.

### 4.3 Score gate semantics

For a Score answer, a threshold such as `fail_at_least: 2` gates on the
argmax level, not on the probability-weighted expected `score` field. The
argmax is the level key with the largest probability. Ties choose the highest
level so a risk gate fails conservatively. The output still exposes the
probability-weighted `score` as a diagnostic value.

This makes an ordinal threshold mean what its name says. A distribution with
`P(level 2) = 0.75` trips `>= 2` even when its expected score is 1.72. A
distribution with `P(level 2) = 0.99` and `P(level 1) = 0.01` also trips it.
Calibration records both the expected-score delta and the argmax level crossing,
but pass/fail uses the argmax crossing.

### 4.4 boundary noise

Calibration noise far from every configured gate threshold is diagnostic only.
It does not void the verdict. Noise within the configured threshold margin, or
noise that straddles a threshold, sets `boundary_noise: true` and makes
`within_tolerance: null` with exit 2.

The same rule applies to Score argmax levels and numeric Noul thresholds. A
candidate that changes an argmax far from a configured threshold is still
reported as drift, but it is not called boundary noise solely for changing.

### 4.5 schema loosening boundary

Blocks that jm interprets remain closed and fail closed:

- chunking and effective defaults;
- state and context limits;
- thresholds and gate operators;
- cache preimage fields;
- coverage counts and reason enums;
- emitter configuration.

Unknown keys in question bodies that jm sends verbatim to Jev pass through.
The validator writes one stderr warning per unknown path. It still validates the
question type, required instructions, state fields, and criteria required to
form the wire request. V3 locks the proven boundary: Noul criteria remain the
two `true` and `false` criteria required by the boolean wire conversion. Score
criteria become an ordered non-empty list with at least two levels; the wire
uses the list as supplied and answer normalization maps levels to `0..n-1`.
The V8 tests cover the existing three-level client fixture and the four-level
built-in preset. No other score shape is accepted without a passing wire and
parser fixture. The implementation must not invent API capabilities.

### 4.6 cache invariant

The cache remains content addressed and complete-answer only. Every v3 change
must preserve these properties:

- equal semantic state plus equal preset battery gives one reusable answer;
- identity and position changes alone do not force a miss;
- a changed question, semantic context, model, effective chunking, or limit
  gives a new key;
- failed and partial calls never publish a complete answer;
- coverage still reports cache hits as judged states.

Distillation remains a non-goal pending Henry's TypeSafe Terms of Service check.
The cache-as-dataset flywheel remains in scope.

## 5. v3 input and preset semantics

### 5.1 raw states

V3 adds `--by state`. It reads one JSON object per JSONL line with this exact
shape:

```json
{
  "state_ref": "case-17",
  "focus": "text to judge",
  "context": {
    "heading": "release",
    "query": "contains the launch decision"
  }
}
```

`state_ref` and `focus` are required. `context` is required and must be an
object. Unknown context keys are allowed because raw states are the universal
adaptor input, but jm still applies byte limits. Duplicate or empty state refs
are input errors with a source locator. A raw-state input error is not a formed
state, so it does not increase `discovered` and makes coverage partial.

The `state_ref` is preserved in result and error records. It is never added to
the cache preimage. `--by state` is compatible with every preset unless the
preset explicitly excludes it.

### 5.2 preset parameters

V3 adds repeatable `--param key=value`. Each parameter is a string mapped to
`context.key` before validation and cache lookup. A key must match
`[a-z][a-z0-9_]*`. The final parameter set must satisfy every parameter field
named by `state_fields`.

An unknown parameter is a usage error with exit 64. A missing required
parameter is a usage error with exit 64. Duplicate keys are a usage error.
The existing `--query` and `--predicate` short forms remain aliases that map to
the same parameter path. They cannot conflict with `--param`.

Parameters are invocation data, not preset text. They appear in formed state
context and in the semantic cache projection when a question names them.

### 5.3 state-field validation

The effective chunker declares its context keys. V3 uses this inventory:

| Chunker | Context keys |
| --- | --- |
| `state` | keys supplied by the raw state |
| `file` | `language`, `metadata`, `path`, plus parameters |
| `line` | `line`, `source`, `surrounding`, `unit`, plus parameters |
| `para` | `heading`, `paragraph`, `source`, `surrounding`, `unit`, plus parameters |
| `record` | `metadata`, `unit`, plus parameters |
| `hunk` | `changed_tests`, `file`, `hunk_header`, `surrounding`, `unit` |

If a question names a context key that the effective chunker cannot provide,
jm writes a stderr warning naming the question, field, and chunker. The run
continues. The absent field is not synthesized. This warning does not change
exit code or coverage counts.

## 6. cache v3

### 6.1 re-key rule

The v3 preimage is:

```json
{
  "cache_schema": "jm-answer/v3",
  "model": "configured-model",
  "preset": "jgrep",
  "preset_version": "1",
  "preset_schema": "jm.preset/v3",
  "chunking": {
    "by": "para",
    "context_paragraphs": 0,
    "limits": {
      "focus_bytes": 16384,
      "context_field_bytes": 4096,
      "state_bytes": 32768
    }
  },
  "question_battery_ref": "sha256:...",
  "semantic_state": {
    "focus": "...",
    "context": {
      "query": "...",
      "heading": "...",
      "surrounding": "..."
    }
  }
}
```

The semantic context projection includes context keys named by the question
battery, except for `state_ref` and chunker identity or position fields such
as `line`, `paragraph`, and hunk locator data. A field such as `file` remains
when the battery names it as evidence. `source`, `path`, and `unit` are
identity fields unless a question explicitly makes one semantic evidence.
The projection is sorted and normalized before hashing.

The preimage never includes `state_ref`, ordinal position, or a positional
subunit number. The state reference remains in output records only. This makes
identical text in two positions share an answer when their semantic context is
equal.

The effective chunking object records every default that can change state
formation. `--by line` therefore records its effective `context_lines` value,
even when the user did not pass the option. Null is not used for an active
default.

### 6.2 battery deduplication

The resolved question battery is stored once under a content hash scoped to
`(preset, preset_version, question_battery_hash)`. A cache entry stores the
reference and the battery hash, not a repeated copy of the full battery. An
export resolves the reference and emits the same v2 training-shaped fields.

The battery hash changes when any interpreted question text, criteria, type,
state field, or pass-through wire field changes.

Presets that use v3-only features declare `jm.preset/v3`. V1 and v2 preset
files remain readable for migration and inspection, but they cannot request
v3-only chunkers, parameters, or output modes without an explicit schema update.

### 6.3 invalidation and counts

The cache schema changes to `jm-answer/v3`. V3 performs one full cache
invalidation at rollout. This is an accepted migration cost because old keys
contain the fields that v3 must remove. Later key changes are content based.

Cache hits remain judged states. They contribute one to `judged`, one to
`emitted` before filtering, and zero to `failed`. A cache hit does not make a
network call.

## 7. chunkers and state formation

### 7.1 bounded surrounding context

When surrounding material exceeds `context_field_bytes`, the chunker truncates
it to a deterministic UTF-8 boundary and adds the ASCII marker
`[... surrounding truncated ...]`. The final field stays within the limit.
The chunk is judged, not rejected, and coverage does not gain a
`context_limit` skip for this case. Required identity, parameter, and complete
state limits still fail closed.

### 7.2 library defaults

Calling a library chunker without a rejection collector must not crash on an
ordinary markdown document only because a neighbour is large. The safe default
is the same bounded behavior as the CLI. A caller may still choose a strict
mode for tests, but the public default forms a state with bounded context.

### 7.3 hunk parser

The hunk parser validates body lines against unified diff syntax. A body line
must begin with a space, `+`, `-`, or the exact no-newline marker. A line with
any other prefix ends the current hunk parse and produces an `input_error`
with a source locator. It must not swallow later file headers or hunks.

Valid zero-count hunks, quoted paths, renames, deletes, binaries, CRLF, and
the no-newline marker keep their existing parse behavior.

### 7.4 paragraph and file behavior

The paragraph chunker skips units that contain only a Markdown heading. The
heading remains available as `context.heading` on the next meaningful unit.

`--by file` remains a whole-file mode. If the focus exceeds `focus_bytes`, jm
rejects it with a `context_limit` skip and documents this behavior in help.
V3 does not silently split a file into arbitrary byte fragments. Callers that
need splitting use `--by para`, `--by line`, or `--by state`.

The `context_lines` key is removed from the hunk preset because the hunk
chunker does not consume it. Hunk context comes from the supplied unified diff.

### 7.5 metadata and fields

V5 exposes `--metadata-fields key[,key...]` for record input. The selected
fields populate `context.metadata` and are included in the semantic cache
projection only when questions name them.

The chunker and state-field rules are validated before Jev calls. A warning for
an unavailable context field does not create a fake value, a partial answer, or
an extra coverage count.

## 8. gate and calibration semantics

### 8.1 empty input

An empty finite input produces no input-error record and prints
`jm: no hunks found` for empty hunk input, or `jm: no states found` for other
empty input. Its coverage record is complete with all five counts equal to
zero. It has no coverage reason.

For a gate with `--require-states 1`, the gate exits 2 for too few states. With
`--require-states 0`, ordinary vacuous truth applies: `any(...)` is false and
`all(...)` is true. Because a policy is a failure condition, the former exits
0 and the latter exits 1. The output still has one terminal coverage record.

Binary-only or header-only diffs use the same no-hunks message. They do not
become an API failure.

### 8.2 policy filter

`run` and `jfilter` add a policy filter that reuses the gate grammar:

```text
jm jfilter 'describes a failed payment' --filter policy \
  --filter-policy 'any(satisfies_predicate.noul >= 0.75)'
```

The policy is evaluated per result record. A matching record is emitted. A
non-matching successful result is suppressed. Errors, partial results, skip
summaries, and coverage remain visible. The filter does not change coverage
counts or gate exit semantics.

`--filter=keep` remains as the short form for one preset-owned keep threshold.

### 8.3 calibration

Calibration uses the same effective gate value as the gate evaluator. For
Score thresholds, it records `baseline_argmax`, `candidate_argmax`, and
`argmax_crossing`; it does not use the expected score to decide a threshold
crossing.

Calibration submits candidate cases through the shared runner pool. The
default concurrency is four, and the same retry and adaptive-window policy
applies. Candidate calls never read or overwrite the baseline cache entry.

The calibration exit codes remain:

| Code | Meaning |
| --- | --- |
| `0` | qualifying cases completed and all tolerances passed |
| `1` | observed drift exceeded a configured tolerance |
| `2` | operational error, mixed model provenance, boundary noise, or no qualifying cases |
| `64` | invalid command, preset, or tolerance |

`no qualifying cases` is not a passing zero delta. It produces a summary with
`within_tolerance: null` and exit 2.

## 9. output and composition

### 9.1 metrics

The default result record remains compact. `--metrics` opts into:

```json
{
  "meta": {
    "usage": {"input_tokens": 120, "output_tokens": 20},
    "latency_ms": 312
  }
}
```

The terminal coverage record then adds `usage_totals` and `latency_ms_total`.
Usage sums only numeric fields. Cache hits contribute stored usage and zero new
latency. Without `--metrics`, these fields are absent from per-state and
coverage output. This keeps the default record contract stable.

### 9.2 jfilter passthrough

`jm jfilter --emit=input` re-emits the original JSON object for every matching
record, in input order. It is supported only for `--by record`; other chunkers
return usage error 64. The original object is held in an emitter sidecar and
is never sent to Jev as an extra state field or added to the cache preimage.

For `--by file`, `--emit=input` emits the normalized path. The canonical
judgment JSONL remains available with the default emitter mode. In passthrough
mode, stdout contains only matching input objects or paths. The emitter writes
non-result records and the terminal coverage record as JSONL to stderr, and
keeps the same exit code rules. This is the one intentional stdout exception
to the canonical judgment stream, because passthrough must compose as a
grep-like input stream.

### 9.3 input and streaming

`--input -` means stdin. It is equivalent to omitting `--input`. A literal
filesystem path named `-` requires an explicit path form that resolves to a
file.

The runner yields the first ordered result as soon as its bounded input window
allows. It does not wait for every state to complete. A downstream `head` may
close the pipe; jm exits quietly after closing the broken stream. States that
already completed may remain cached, which is allowed and documented.

## 10. preset and CLI polish

V8 makes these user-facing changes:

- If a cwd preset shadows a built-in preset of the same name, jm warns on
  stderr. An explicit `./name.yml` remains the way to request the shadow.
- Defaults fill boilerplate for `chunking.limits`, compatible chunkers, output
  fields, and the pretty template. The resolved preset still records all
  effective values in provenance and the cache preimage.
- `--by`, `--max-chunks`, `--format`, `--filter`, and `--query` get help text.
  `jm --version` prints the package version and exits 0.
- `jm preset show` prints the resolved source YAML. It does not convert the
  source to JSON. `preset list` and `preset validate` keep their machine-readable
  metadata output.
- The built-in `jgrep` preset pins `context_lines: 0` for line overrides.
  Generic line input keeps its default of one adjacent line. Help states this
  asymmetry.
- Unknown fields in question bodies pass through with warnings as defined in
  section 4.5. jm-interpreted blocks remain closed.

These are presentation changes. They do not alter judgment counts or exit
codes unless a malformed configuration is rejected with 64.

## 11. compatibility and exit contract

The v3 judgment exit codes remain:

| Code | Meaning |
| --- | --- |
| `0` | complete coverage and no active failure condition |
| `1` | a complete gate or policy filter found the requested failure condition |
| `2` | operational error, incomplete coverage, too few required states, or an indeterminate gate |
| `64` | invalid command, preset, parameter, policy, or option combination |

`judge()` does not return an exit code. The CLI derives it from terminal
coverage and gate results. A library caller can inspect the same `CoverageRecord`
and `GateResult` data without parsing text.

The terminal coverage record always has exactly these five count fields:
`discovered`, `judged`, `emitted`, `skipped`, and `failed`. V3 adds optional
metric totals, not a second count system. The invariant remains:

```text
discovered = judged + skipped
failed <= judged
```

Output filtering does not reduce `emitted`. It only suppresses visible result
records. This prevents a filtered empty output from claiming that no states
were judged.

## 12. non-goals

V3 carries forward these v2 non-goals:

- watch mode, streaming windowing, and incremental windowing;
- a `--hint` option or query expansion;
- injection hardening for hostile or multi-tenant state;
- a native TypeSafe API fallback or a second transport;
- embeddings, a vector database, a hosted search service, or a heavy prefilter;
- automatic threshold updates;
- a remote or shared cache;
- generated explanations, model prose, broad policy language, and arithmetic
  inside Jev questions;
- local model training or distillation before Henry's TypeSafe Terms of Service
  check.

V3 streaming means lazy finite iteration. It does not reopen watch mode or
  unbounded input. V3 model provenance does not reopen distillation or a second
  backend. V3 raw-state input does not make arbitrary hostile state safe for CI.

## 13. task ladder

Every task lists its dependency, files, tests, and exit criteria. Each task
preserves the output and coverage rules in section 11.

### V1: reliability and provenance

**Depends on:** v2 complete. No V2 refactor dependency.

**Files touched:**
