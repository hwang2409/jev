# jmap v1 implementation plan

## goal

build the `jmap` Python package described by
`jmap/docs/superpowers/specs/2026-09-22-jmap-design.md`. `jmap` applies typed
Jev question batteries to finite input states, emits canonical JSONL, stores
content-addressed answers, and evaluates small CI gate policies.

This plan translates the merged design into nine dependency-ordered
implementation lanes. Each lane is one implement-lane PR and leaves the tree
green. The plan does not redesign the spec.

In scope:

- the `run`, `jgrep`, `jfilter`, `gate`, `preset`, and `cache` commands;
- `line`, `para`, `hunk`, `file`, and `record` finite chunkers;
- one batched question request per state, with bounded retries;
- typed result, partial-result, error, and coverage JSONL;
- deterministic scan-with-cap behavior;
- local content-addressed cache, clear, and export;
- the three exact v1 preset batteries;
- typed boolean policies, aggregate `any` and `all`, and `--require-states`;
- offline tests and evals through the injected `judge_fn` seam;
- one opt-in live-API smoke script gated by `JEV_API_KEY`.

Out of scope:

- watch mode, stream windowing, and incremental re-judgment;
- embedding prefiltering, query expansion, and `--hint`;
- local models, distillation, remote caches, and shared caches;
- generated explanations, full-text indexes, and broad policy language;
- CI-guard hardening for hostile or multi-tenant input;
- automatic model upgrades and threshold migration.

## architecture

`jmap.cli` parses commands and formats only the command-specific output.
`jmap.presets` resolves and validates YAML presets. `jmap.chunkers` turns
finite input into stable formed states. `jmap.runner` admits those states,
checks limits, reads and writes the cache, calls the injected `judge_fn`, and
emits records. `jmap.api` adapts the HTTP endpoint to that seam. `jmap.answers`
owns typed response validation and canonical record values. `jmap.cache`
owns content-addressed storage and export. `jmap.gates` parses and evaluates
typed failure-condition policies.

The shared seam is:

```text
judge_fn(state, questions, model) -> typed response
```

The runner uses the real HTTP client by default. Tests and evals inject a
deterministic fake. One state sends its full question battery in one request.
The seam records cache hits, incomplete responses, and errors without calling
the Jev API in normal tests.

The state path is:

```text
finite input -> formed states -> byte-limit checks -> scan cap
    -> cache lookup -> one full-battery judge call -> typed record
    -> optional result filter -> terminal coverage record
```

`gate` consumes the same records and fails closed on operational errors,
missing answers, affected unvisited states, or fewer than the required number
of judged states.

## tech stack

- Python `>=3.12`.
- `uv` project management, matching `laya/` and `harness/` conventions.
- `httpx` for the hand-rolled API client.
- `pyyaml` for reviewable presets.
- `pytest` for tests and offline evals.
- `ruff` for linting.
- `hatchling` for the package build and `jmap` console script.
- no Jev API dependency for unit tests or offline evals.

The initial package is CI-less. The lanes use `uv run pytest` and `uv run ruff`
locally. A later repository-level CI change is outside this ticket.

## global constraints

- Work only in `jmap/` for implementation lanes.
- Keep the package layout exactly as the spec defines:
  `jmap/__init__.py`, `__main__.py`, `cli.py`, `api.py`, `answers.py`,
  `cache.py`, `chunkers.py`, `gates.py`, `presets.py`, `runner.py`, and
  `presets/{jgrep,jfilter,diff-risk-heat}.yml`.
- Keep tests in `jmap/tests/` with the named files in the spec. A supporting
  eval test may be `jmap/tests/test_eval.py`; it does not add a package module.
- Use deterministic ordering for input units, questions, cache JSON, output,
  skip summaries, and exported triples.
- Treat all input text as data. Never execute or interpret focus or context as
  instructions.
- Enforce UTF-8 byte limits. Never silently truncate a required identity,
  user parameter, focus, context field, or complete state.
- Keep `JEV_API_KEY` out of records, cache files, exports, logs, and errors.
- Keep judgment stdout limited to canonical JSONL records. Human output goes
  to stderr. Non-judgment command stdout follows its separate contract.
- Use the exact four record types: `result`, `partial_result`, `error`, and
  `coverage`.
- Do not change record schemas, preset batteries, thresholds, or criteria text.
  Any change requires an orchestrator-approved spec amendment PR first.
- Keep unit tests offline. Only the explicit smoke script may call the live API,
  and it must require `JEV_API_KEY` and use a tiny finite state count.
- Do not implement watch mode, streaming, prefiltering, hints, local backends,
  remote caches, or hostile-input hardening.
- Every lane must run its listed verification command before its PR is opened.
- Run a subtractive simplification pass over the final implementation diff.

state and chunker contracts:

- `line`: one logical line, with source identity, line number, and bounded
  adjacent-line context;
- `para`: blank-line-delimited paragraph, with nearest heading, source
  identity, paragraph identity, and bounded adjacent paragraphs; default for
  `jgrep`;
- `hunk`: one unified diff hunk, including added and removed lines, with file

  default for `diff-risk-heat`;

- required identity and user-parameter fields over their limit are rejected;
  oversized focus is split only when the chunker supports explicit subunits;
- chunkers discover all formed states before applying `max_chunks`;
- states beyond a cap are skipped in deterministic input order and retain stable
  refs for the later skip summary;
- the runner records `discovered`, `judged`, `emitted`, `skipped`, and `failed`;
  this task owns formed-state discovery and skip accounting, while task 4 owns
  the final record output.

### 3. add the API client behind the seam

status: depends on tasks 1 and 2.

spec sections: 2.3, 2.4, 8.1, 8.3, 8.4, and 9.1. Implement the `httpx`
client that satisfies the seam and sends one full question battery per state.
Use `POST https://api.typesafe.ai/v1/systemone` with
`Authorization: Bearer $JEV_API_KEY`. Presets provide a pinned resolved model;
`jev-latest` is invalid.

files:

- create `jmap/jmap/api.py`;
- extend `jmap/jmap/answers.py` with typed API request and response validation;
- extend `jmap/jmap/runner.py` only where the client is injected as the default
  `judge_fn`;
- create or extend `jmap/tests/test_runner.py` for client seam behavior;
- create `jmap/tests/test_answers.py` for response parsing and validation.

API contracts:

- request JSON is:

  ```json
  {
    "state": {"focus": "...", "context": {"state_ref": "..."}},
    "model": "jev-1.13.0",
    "questions": {
      "question_id": {
        "type": "noul",
        "instructions": {"question": "...", "state_fields": ["focus"]}
      }
    }
  }
  ```

- the API key is read at call time and never included in an exception, record,
  cache value, or log;
- `429`, `529`, and network timeouts retry with exponential backoff and jitter;
  honor valid `Retry-After`; cap total attempts at three;
- `401` and `422` do not retry;
- `--concurrency` bounds in-flight requests and defaults to a conservative small
  value; no question is split into its own request;
- a successful response missing any requested question retries exactly once
  with the original full battery and the same cache key;
- if the second response is still incomplete, return parsed answers plus
  `missing_questions`; never cache it as a complete success;
- typed validation accepts Noul answers with only `type` and `noul`, Choice
  answers with `type`, `choice`, `probabilities`, and `confidence`, and Score
  answers with `type`, `score`, `legend`, `probabilities`, and `confidence`;
- call confidence is not accepted on Noul answers and is not derived into any
  output, cache, export, or eval field.

tdd and verification:

1. In `jmap/tests/test_answers.py`, add fixtures for valid Noul, Choice, and
   Score responses, missing fields, unknown question IDs, bad primitive types,
   and forbidden Noul confidence.
2. In `jmap/tests/test_runner.py`, use an `httpx.MockTransport` and assert the
   exact URL, bearer header, model, state, and full question battery.
3. Assert retry sequences for `429`, `529`, timeout, `401`, and `422`. Patch
   sleep and jitter so the test is deterministic; assert no more than three
   total attempts and that `Retry-After` wins when valid.
4. Assert one full-battery retry for an incomplete response, then assert the
   returned missing IDs.
5. Assert that error messages and structured error values contain no API key.
6. Run `cd jmap && uv run pytest -q tests/test_answers.py tests/test_runner.py`.
7. Run `cd jmap && uv run ruff check .`.

### 4. add canonical answers, JSONL records, exit codes, and coverage

status: depends on tasks 1 through 3.

spec sections: 2.5, 2.6, 2.7, 3.3, 8.2, and 8.4. Make the record and output
contracts executable. The runner must flush per-state records, continue
independent finite states where possible, and emit one terminal coverage record.

files:

- extend `jmap/jmap/answers.py` with canonical typed answer and record models;
- extend `jmap/jmap/runner.py` with JSONL emission, filtering, summaries, and
  exit status calculation;
- create or extend `jmap/tests/test_answers.py`;
- create or extend `jmap/tests/test_runner.py`.

canonical record contracts:

The judgment commands are `run`, `jgrep`, `jfilter`, and `gate`. For those
commands, stdout contains only one JSON object per line, and every object
matches one of these four record types. No other stdout record, header,
progress message, or summary exists. Human-facing run headers, progress,
warnings, pretty output, and process summaries go to stderr. The non-judgment
commands have separate stdout contracts.

The four record types are `result`, `partial_result`, `error`, and `coverage`.
The `error` type has a per-state error variant and a skip-summary variant. The
first three describe one finite state or one operational event. The terminal
`coverage` record describes the whole invocation. A skip-summary error groups
many formed states by one reason and boundary.

The common metadata object has these required fields:

```json
{
  "preset": "jgrep",
  "preset_version": "1",
  "model": "jev-1.13.0",
  "chunker": "para",
  "cache": "miss"
}
```

`cache` is one of `hit`, `miss`, or `not_applicable`.

A complete state has this shape:

```json
{
  "record_type": "result",
  "state_ref": "src/payments.py@@-40,8+40,12",
  "answers": {"change_scope": {"type": "score", "score": 2.13, "legend": {"0": "...", "1": "...", "2": "...", "3": "..."}, "probabilities": {"0": 0.01, "1": 0.08, "2": 0.78, "3": 0.13}, "confidence": 0.86}},
  "meta": {"preset": "diff-risk-heat", "preset_version": "1", "model": "jev-1.13.0", "chunker": "hunk", "cache": "miss"}
}
```

`answers` contains every requested question. A `noul` answer has `type` and
`noul`. A `choice` answer has `type`, `choice`, `probabilities`, and
`confidence`. A `score` answer has `type`, `score`, `legend`, `probabilities`,
and `confidence`. The CLI does not reduce a score to a magnitude.

A response that remains incomplete after the retry has this one canonical
partial shape. `answers` contains only parsed answers, `missing_questions` is
non-empty, and `meta.partial` is `true`:

```json
{
  "record_type": "partial_result",
  "state_ref": "src/payments.py@@-40,8+40,12",
  "answers": {"change_scope": {"type": "score", "score": 2.13, "legend": {"0": "...", "1": "...", "2": "...", "3": "..."}, "probabilities": {"0": 0.01, "1": 0.08, "2": 0.78, "3": 0.13}, "confidence": 0.86}},
  "missing_questions": ["likely_breakage"],
  "meta": {"preset": "diff-risk-heat", "preset_version": "1", "model": "jev-1.13.0", "chunker": "hunk", "cache": "miss", "partial": true}
}
```

An API or parse failure for a judged state has `state_ref`, no `source_ref`,
and `error.kind` of `api_error` or `malformed_answer`. `http_status` is an
integer or `null`; `attempts` is a non-negative integer. Scan-cap and
context-limit skips use the skip-summary error variant below, not one error
record per skipped state.

```json
{
  "record_type": "error",
  "state_ref": "src/payments.py@@-40,8+40,12",
  "error": {"kind": "api_error", "message": "request failed", "http_status": 503, "attempts": 3},
  "meta": {"preset": "diff-risk-heat", "preset_version": "1", "model": "jev-1.13.0", "chunker": "hunk", "cache": "miss"}
}
```

An input failure before a state identity exists uses the same `error` record
type, with `state_ref: null`, a required `source_ref` in the exact locator
form `<source>:byte=<integer>,line=<integer>`, and `error.kind: "input_error"`.
Its `meta.cache` is `"not_applicable"`. The runner never uses an ordinal as a
fallback identity.

```json
{
  "record_type": "error",
  "state_ref": null,
  "source_ref": "stdin:byte=128,line=4",
  "error": {"kind": "input_error", "message": "invalid JSON record", "http_status": null, "attempts": 0},
  "meta": {"preset": "jfilter", "preset_version": "1", "model": "jev-1.13.0", "chunker": "record", "cache": "not_applicable"}
}
```

The closed `error.kind` enum is `api_error`, `malformed_answer`, `scan_cap`,
`context_limit`, or `input_error`. `scan_cap` and `context_limit` are the
skip-summary variant. That variant has `state_ref: null`, `source_ref: null`,
one per-reason count, and at most eight sample refs.

```json
{
  "record_type": "error",
  "state_ref": null,
  "source_ref": null,
  "error": {"kind": "scan_cap", "message": "scan cap reached before visit", "http_status": null, "attempts": 0, "skip_summary": {"boundary": "max_chunks=256", "count": 685, "sample_refs": ["notes.md:paragraph=257", "notes.md:paragraph=258"]}},
  "meta": {"preset": "jgrep", "preset_version": "1", "model": "jev-1.13.0", "chunker": "para", "cache": "not_applicable"}
}
```

Every judgment invocation emits exactly one coverage record:

```json
{
  "record_type": "coverage",
  "coverage": "complete",
  "coverage_counts": {"discovered": 1, "judged": 1, "emitted": 1, "skipped": 0, "failed": 0},
  "coverage_reasons": [],
  "meta": {"preset": "diff-risk-heat", "preset_version": "1", "model": "jev-1.13.0", "chunker": "hunk", "cache": "not_applicable"}
}
```

`coverage` is `complete` or `partial`. For formed states, the counts contain
`discovered`, `judged`, `emitted`, `skipped`, and `failed`. A formed state is
discovered when the chunker has parsed one input unit, assigned its stable
`state_ref`, and materialized its focus and context, before cache or API
admission. Judged states are discovered states admitted to that path, including
states that fail there. Skipped states never enter that path. `emitted` counts
per-state records for judged states before result filtering; skip-summary
records are not per-state records. `failed` is the subset of judged states with
an operational error. Input errors before a stable identity exists are not
formed states and are excluded from these counts. The counts always satisfy
`discovered = judged + skipped` and
`skipped = sum(skip_summary.count)` across all skip-summary records.

The closed `coverage_reasons` enum is `scan_cap`, `input_error`,
`context_limit`, `api_error`, `malformed_answer`, or `partial_answer`. It is
empty only for complete coverage.

`--format=jsonl` is the default. `--format=pretty` renders selected result
records to stderr; stdout still carries the canonical JSONL records. A filter
can suppress only successful result records. Error, partial-result, and
coverage records remain on stdout.

Exit `0` means complete and no active gate failure, `1` means a true failure
predicate, `2` means operational failure or fail-closed gate, and `64` means
usage, preset validation, or policy syntax error. Usage errors before
execution emit no coverage. Operational errors emit partial coverage. A
complete gate can exit `1` but still has complete coverage.

tdd and verification:

1. Add exact JSON assertions for one complete result of each answer type, one
   partial result, one per-state API error, one input error, one skip summary,
   and one coverage record.
2. Add tests for stdout-only JSONL and stderr-only warnings, pretty output,
   result filtering, skip samples capped at eight refs, and record flush order.
   The boundary test keeps eight refs and drops the ninth.
3. Add property-style parametrized assertions for the three coverage equations
   across complete, cap-skipped, input-error, API-error, and partial-answer
   fixtures.
4. Add exit tests for the non-gate runner paths that task 4 owns, including
   complete success and operational failure.
5. Run `cd jmap && uv run pytest -q tests/test_answers.py tests/test_runner.py`.
6. Run `cd jmap && uv run ruff check .`.

rollback: revert the task 4 commit. No cache entries or external API state are

### 5. add the content-addressed cache, clear, and export

status: depends on tasks 1 through 4.

spec section: 6. Implement local answer storage without a database, TTL,
eviction daemon, remote cache, or shared cache.

files:

- create `jmap/jmap/cache.py`;
- extend `jmap/jmap/runner.py` with cache lookup and publish hooks;
- extend `jmap/jmap/answers.py` only for cache/export serialization if needed;
- create or extend `jmap/tests/test_cache.py`;
- extend `jmap/tests/test_runner.py` for hit and miss metadata.

cache key contract:

- compute SHA-256 over canonical UTF-8 JSON with sorted object keys and no
  insignificant whitespace;
- include exactly `cache_schema`, pinned `model`, `preset`, `preset_version`,
  fully resolved `chunking` including effective limits, fully resolved
  `question_battery`, and fully resolved `state`;
- include effective limits even when they equal defaults;
- changing question text, criteria, state context, chunker behavior, preset
  version, or model must change the key;
- do not include the endpoint; endpoint changes require a cache schema version
  change;
- store values under
  `${JMAP_CACHE_DIR:-~/.cache/jmap}/answers/ab/cd/<sha256>.json`, with the
  first two and next two digest characters as directories;
- store key inputs, typed answers, optional usage, model, preset identity,
  creation time, and protocol version;
- publish through a temporary file and atomic rename, with a lock or equivalent
  that prevents incomplete values;
- malformed or partial values are misses; a live partial or failed request is
  never stored as a successful answer;
- a hit returns the same typed answers with `meta.cache="hit"` and does not
  call Jev;
- `cache clear --preset NAME` removes only matching preset entries;

The cache key preimage has this exact JSON shape:

```json
{
  "cache_schema": "jmap-answer/v1",
  "model": "jev-1.13.0",
  "preset": "jgrep",
  "preset_version": "1",
  "chunking": {
    "by":"para",
    "context_paragraphs":0,
    "limits": {
      "focus_bytes":16384,
      "context_field_bytes":4096,
      "state_bytes":32768
    }
  },
  "question_battery": {
    "matches_query": {"type":"noul","instructions":"...","criteria":{}}
  },
  "state": {
    "focus": "...",
    "context": {"file":"notes/intro.md","query":"launch decision","state_ref":"notes/intro.md#p3"}
  }
}
```

`cache export` writes one training-shaped triple per question answer. It does
not train or upload anything. It emits no coverage record because it has no
coverage concept. Its exact JSON shape is:

  ```json
  {
    "state": {
      "focus": "...",
      "context": {"file":"notes/intro.md","query":"launch decision","state_ref":"notes/intro.md#p3"}
    },
    "question_id": "matches_query",
    "question": {
      "type": "noul",
  ```

grammar and semantic contracts:

```text
predicate := comparison
           | "not" predicate
           | "(" predicate ")"
           | predicate "and" predicate
           | predicate "or" predicate

comparison := field (">=" | ">" | "<=" | "<" | "==" | "!=") literal
field      := question_id "." answer_field
literal    := number | quoted_string | "true" | "false"
```

  operators are left-associative; parentheses override precedence;

  pass; an explicit non-negative `N` changes only that requirement;
- the validator rejects Noul thresholds on Score or Choice fields, Score
  thresholds on Noul or Choice fields, and values not equal to the preset's
  pinned threshold;
- policy evaluation uses typed answer fields, not formatted text;
- true policy means exit `1`, false means no policy failure, and any
  operational error, malformed answer, missing answer, or affected unvisited
  state means exit `2`.
